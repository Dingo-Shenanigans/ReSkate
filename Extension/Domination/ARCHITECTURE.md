# Domination: how it's built

For ReSkate's maintainers and their coding agents: where the game logic is, what it depends on, and how to change it without breaking multiplayer. README.md covers playing and park files.

## Two layers

**1. The rules: no game, no Windows.** Plain C++20 plus ReSkate's `Json`. Every rule that decides who owns what and whether players agree lives here, and the tests cover all of it.

| File | Holds |
|---|---|
| `domination_model.h/.cpp` | Parks and spots (`parse_park`, `spot_at`), reading tricks from score-HUD values (`TrickWatch`), the board (`Board`: claims, owners, history), a round's results (`round_stats`, `ranked`), teams (`balance_teams`) |
| `domination_sync.h/.cpp` | Multiplayer rounds (`sync::Node`): who runs rounds, joining, the round's clock, teams, board snapshots, the end, the results |
| `domination_wire.h/.cpp` | The messages between players (`wire::encode` / `decode`, version 4) |
| `Test/domination_tests.cpp` | Parks, trick reading, the board, results, teams, the wire format, the built-in parks |
| `Test/domination_net_tests.cpp` | Whole rounds between up to 16 simulated players over a bad network |

**2. The game side: skate. and ReSkate.** It reads the game and draws on it, and feeds the rules.

| File | Holds |
|---|---|
| `domination.cpp` | Rounds: the game around a `sync::Node` (session roster in, messages out, events to toasts and sounds, tricks to claims, the start teleport); the console verbs; `snapshot()` for menus; `overlay_view()` for the overlay |
| `domination_hud.cpp` | Tricks read from skate.'s `ScoringHUDViewModel` (field hashes from the game's type data) |
| `domination_files.cpp` | Park files (a parks folder, map mods, the built-in parks), the chosen park, whether its map is installed, spot outlines measured on the ground |
| `domination_overlay.cpp` | Drawing: markers, outlines, edge arrows, HUD, feed, results |
| `domination_commands.cpp` | The `domination ...` console commands |
| `domination_internal.h` | The game side's shared state (not for other code) |
| `domination_parks.h` | The built-in parks: five on San Vansterdam and five on the Skate 3 map mod, generated by `tools/make_builtin.py` from `parks/*.json` |
| `domination_tools.cpp` | Park-making: `domination scan` (height maps), `tp` and `survey` (MAKING-PARKS.md) |
| `parks/`, `tools/` | The built-in parks' files and specs; the scripts that build parks, build them in, and pack them as mods |
| `domination.h` | The API for the rest of ReSkate |

## Touchpoints outside this folder

| Where | What |
|---|---|
| `Runtime/runtime_init.cpp` | `domination::start(base)` |
| `Runtime/client_tick.cpp` | `domination::on_client_tick()` every tick; `domination::set_level(level)` |
| `Extension/Multiplayer/Session/session.cpp` | Throwdown messages starting with `0xD0` go to `domination::receive`, not the throwdown relay; `domination::take_outgoing()` is sent as throwdown packets |
| `Extension/UI/Overlay/overlay_render.cpp` | `domination_pending()` / `draw_domination()` |
| `Extension/Console/commands.*` | `register_domination_commands` |
| `Extension/Profile/local_profile_*`, `Extension/Objects/local_placements_runtime.*` | `teleport_local_skater_heading` (a teleport that faces a heading), `local_surface_hit` (ReSkate's own native ray between two points: what the camera can see of the outlines) |
| `cmake/Runtime.cmake`, `cmake/UI.cmake`, `CMakeLists.txt` | Sources and the tests (`DINGOSDK_BUILD_DOMINATION_TESTS`) |

With Custom Multiplayer: `domination_menu.cpp` registers the mode's panel, built from `snapshot()`. It is compiled with `DINGOSDK_CUSTOM_MODES` only when `Extension/CustomModes/custom_modes.h` is in the tree (`cmake/Runtime.cmake`); without it, `register_custom_mode()` does nothing.

Play counts: a round played to the end adds one to the player's `ReSkate.Domination.Rounds`, `.Park.<id>`, and with others `.Online` (and `.Won`), through `profile_runtime::set_local_values` (the store Hall of Meat keeps its bests in). They stay on the player's PC: nothing is sent anywhere.

## One tick

1. **Client tick** → `on_client_tick()`:
   - the session's roster (players, host, dedicated server or not) → `Node::set_roster`;
   - `Node::tick(ms)`: resends, the authority's duties, the end;
   - `Node::take_outgoing()` → the session's throwdown packets;
   - `Node::take_events()` → toasts, sounds, flashes, the results at the end;
   - the score HUD → `TrickSignals` → `TrickWatch::update`;
   - a `landed` trick → `Node::claim(spot, points, ms)`;
   - the spots' outlines, a little at a time: the ground under each spot's edge, measured once the
     skater is near it (collision loads only around them), then `fill_in` and `even_out`.
2. **Session tick** → `receive(sender, bytes)` → `Node::receive`.
3. **Render thread** → `overlay_view()`: a copy of what to draw.

Times are each player's own `steady_clock` in ms. The `Node` never reads a clock itself.

## Using the rules somewhere else

Another game mode, a server or a bot can include `domination_model.h`, `domination_sync.h` and `domination_wire.h` and run `sync::Node`s:
- give each one its roster and the time;
- pass messages between them as bytes;
- call `claim` for tricks.

Two players, in a few lines:

```cpp
#include "Extension/Domination/domination_sync.h"
using namespace dingosdk::domination;

sync::Node a(park_hash, spots), b(park_hash, spots);  // one per player, the same park
a.set_roster({id_a, id_a, {id_b}});                   // self, host, the others
b.set_roster({id_b, id_a, {id_a}});
a.start(now_a, {}, 300, false, round_id);             // the host starts a 5-minute round
// every tick, on each side: tick, then deliver what it put out
a.tick(now_a);
for (auto &bytes : a.take_outgoing()) b.receive(id_a, bytes, now_b);  // b joins at once
b.tick(now_b);
for (auto &bytes : b.take_outgoing()) a.receive(id_b, bytes, now_a);
// a landed trick: its spot and points
b.claim(spot, points, now_b);
// what to show: a.match()->board.owner(spot), a.match()->standings(now_a).rows;
// a.take_events() says what happened (joined, a spot changed hands, the end)
```

`Test/domination_net_tests.cpp` does exactly that for 16 players.

## Rules that keep every player's game in agreement

Break one and players see different owners or results. The network simulation catches most breaks.
- **Ownership** is a pure function of the claims: higher score, then earlier claim (ms since the round started, by the claimant's clock), then lower Steam ID. An equal score never steals. Claims merge in any order and any number of times (`Board::claim` is idempotent).
- **History** keeps every claim that was ever a player's best on a spot, so a round's replay (time held, steals) is the same on every copy.
- **A round's time** is ms since its start. Claims count only inside the play (after the 4 s countdown, before the end). A stopped round ends at the stopper's moment: everyone drops later claims alike.
- **The authority** (the controller while it's in the round, else the lowest ID heard from lately) sets the clock and hands out teams. Teams never move a placed player.
- **Late joiners** hear the round from any participant (every 5 s) and catch up from board snapshots (every 5 s; after the end every 2 s for 10 s, then every 10 s for 3 minutes). Nothing assumes a message arrives.

## Changing things safely

- **A new round option:** a bit in `wire::Option` (teams is the only one now) and in `sync::Options`, its rule in `domination_sync.cpp`, a `domination set` word, the menu panel (`domination_menu.cpp`). Older builds refuse unknown option bits, so bump `wire::version`.
- **A new or changed message:** bump `wire::version` (4 now). Players on other versions are told once why their rounds don't meet.
- **A rule change:** add a scenario to `Test/domination_net_tests.cpp` first.
- **A new park:** a JSON file, shared as a mod (MAKING-PARKS.md). To build one in, add it to `parks/` and run `tools/make_builtin.py`. Changing a park's spot ids changes its hash, and players on different park versions can't play together (they're told).
- **A new game build:** what breaks first is `domination_hud.cpp`: `ScoringHUDViewModel`'s field hashes and the HUD model lookup. When the model is found, the log names each field's offset, or `missing`.

## Tests

`-DDINGOSDK_BUILD_DOMINATION_TESTS=ON`, then `ctest -R domination`. That runs `domination` and `domination_net`, in a few seconds. Optional:
- `-DDINGOSDK_DOMINATION_PARK=<park.json>` checks a park file against the built-in copy.
